# house-rules.md: Verify 共通チェックリスト正本

## 目的

`/verify` フルモードの V1（形式チェック）と汎用モード（G1）が共通で参照する検収チェックリストの正本。
レビュー担当者の過去5ヶ月・109プロジェクトのセッション発話から採掘した頻出指摘8系統を、○×判定できる
チェック項目として一本化したもの。V1・G1 はここを読み、全項目を対象に照合すること。

## 運用ルール

- レビュー担当者から新しい指摘・差し戻しが出たら、該当する系統（H1〜H8）に1行追記する。
  行末に `<!-- 初出: YYYY-MM-DD -->` を付ける。
- 単発（1回しか出ていない）の指摘は本文に入れず、最下部「観察中（単発）」節に置く。
  同種の指摘が2回目出た時点で本文（該当系統）へ昇格させる。
- チェック項目は増やしすぎない。**H1〜H8 の合計**で30〜55個の範囲を維持する（多すぎると形骸化する）。
  「観察中（単発）」節は件数に含めない。現在 H1〜H8 = 51個（2026-09-03 時点）。55個を超える場合は同数を削るか運用手順側へ移す。
  上限は 2026-09-03 に45個から55個へ引き上げた（consulting-pptx-skill 突合で3項目追加。追記前から48個で旧上限を超えていた）。
- 実行手順（コマンドを叩く・スクショを撮る等）はチェック項目ではない。`SKILL.md` の手順節に置く。

### 2026-09-03 の追記

consulting-pptx-skill（`gozen3ji/consulting-pptx-skill`）の80項目を突合した結果、H6の機械スキャン手順、

## H1. 図表・レイアウトの機械的崩れ（最頻出）

- [ ] 矢印・線・要素同士が重なっていないか <!-- 例:「矢印かぶってる」-->
- [ ] 画像・図が潰れていないか（アスペクト比崩れ）<!-- 例:「画像つぶれてるやないかい」-->
- [ ] コンテンツがフレーム・スライド枠からはみ出していないか <!-- 例:「はみ出てる！図が」-->
- [ ] 文字サイズが小さすぎて可読性を欠いていないか <!-- 例:「小さすぎる。文字が」-->
- [ ] フォントの種類・太さが統一されているか <!-- 例:「フォントがバラバラ」-->
- [ ] スライド系資料のアスペクト比が指定どおり（既定16:9）で統一されているか <!-- 例:「16:9じゃない」-->
- [ ] モバイル幅で画像・図が表示されるか（レスポンシブ崩れ）<!-- 例:「モバイルで絵が表示されない」-->
- [ ] 要素間の高さ・位置が揃っているか <!-- 例:「高さがずれているの気になる」-->

> H1 は**レンダリング結果のスクショに対して**判定する（テキストのみの確認は不可）。
> 撮影手順は `SKILL.md` の該当節を参照。チェック項目ではなく実行手順のためここには置かない。
> PPTX は代替フォント起因の日本語折り返しがスクショ（LibreOffice PDF）では再現しないため、
> `pptx_jp_wrap_check.py` による机上検査も併用する。手順は `SKILL.md` を参照。<!-- 初出: 2026-08-23 -->
> WRAP RISK と BORDERLINE はレンダリングが正常でも解消扱いにしない（PowerPoint 実機でのみ再現するため）。
> テキスト短縮で閾値を切るか、レビュー担当者が実機で表示確認した場合のみ解消。<!-- 初出: 2026-08-31 非公開クライアントA社成果報告pptx。2段落見出しの実機文字切れがすり抜けた件 -->

## H3. 初見者・非専門家への平易さ

- [ ] 業界・社内文脈を知らない読者が読んでわかる表現か <!-- 例:「CHROが見るんだよ？採用プロセスは普段みてない人。その人がみてわかる表現じゃないと意味ない」-->
- [ ] 作成者だけに通じる独自の記号・整理・略記が残っていないか <!-- 例:「作成者しかわからない記号や整理が多すぎる」-->
- [ ] 専門用語は平易な言葉に開かれているか <!-- 例:「専門用語を平易に開いて」-->
- [ ] 略語は初出で正式名称を示すか読者の日常語に言い換えているか <!-- 例:「UCと略すの辞めて」「EAって彼らの言葉？そうでなければ言い換えて」-->
- [ ] 技術記号（ステータスコード等）が非エンジニア読者向けに書き換えられているか <!-- 例:「500とか200OKとかわからないから書き換えて」-->

## H4. 出典・根拠

- [ ] 主張・数値に出典が明記されているか <!-- 例:「ソース不明で少なすぎる」-->
- [ ] 引用の内容が原典と一致しているか <!-- 例:「引用が正しいか検証してほしい」-->
- [ ] 元文献・一次情報へのリンクが添付されているか <!-- 例:「元文献へのリンクほしい」-->
- [ ] 1次情報に基づかない伝聞・推測が主張として扱われていないか <!-- 例:「1次情報ないとしょうがない」-->
- [ ] 出典はキャプション等の定位置に記載されているか <!-- 例:「出典はキャプションにいれてほしい」-->

## H5. 金額・機密の露出

- [ ] 契約金額・単価・累計額が本文・図に直書きされていないか（レビュー担当者の承認の明記がある場合のみ例外）
      <!-- 例:「金額はナシで」「図に金額の記載は不要」-->
- [ ] 人月単価等の内部コスト構造が露出していないか <!-- 例:「人月単価ってこんな顕に書くもの？」-->
- [ ] クライアント自身が取引公表済みでない限り社名が伏せられているか <!-- 例:「社名出さずに」-->
- [ ] 非公開情報（未公表の数値・内部方針等）が紛れ込んでいないか <!-- 例:「非公開情報が出てしまう」-->

## H6. 表記・呼称の統一

- [ ] 正式社名の表記が正本「表記の共通ルール」どおりか（条件はここに再掲しない。正本を読んで判定する）
- [ ] ロゴ・ブランド文脈の英字表記が小文字「pineal」か（英文の文頭・一般英文は対象外）<!-- 例:「Pinealでなくpineal」-->
- [ ] クライアント固有の呼称が社内の記録通りか <!-- 例:「◯◯ですね。ずっとそう呼んでいるので覚えておいて」「正式社名で呼んだ方がいい」-->
- [ ] 人名・社名・固有名詞の誤記・表記ゆれがないか（音声起こし由来の誤変換に注意）<!-- 例: 類似音の別企業名・別人名に誤変換された事例の訂正 -->
- [ ] 「ピネアル社様向け」等の不要な敬称・重複表現がないか <!-- 例:「ピネアル社様向けみたいな表記は不要」-->
- [ ] 図解のラベル・タイトル・説明がすべて日本語になっているか（英語残存なし）
- [ ] 表記ゆれペア（例: メモリ/メモリー、紐付け/紐づけ、サーバ/サーバー、ユーザ/ユーザー、問い合わせ/問合せ、
      打ち合わせ/打合せ）の両方が同一成果物に出現していないか（grep による機械スキャン。
      手順は `SKILL.md` を参照）<!-- 出典: consulting-pptx-skill slide-rules 2026-09-03 -->

> 表記ゆれスキャンの実行手順（対象は html/md/pptx。pptx は `unzip -p file.pptx 'ppt/slides/*.xml'` でテキスト抽出してから照合する）は
> チェック項目ではなく実行手順のためここには置かない。`SKILL.md` を参照。

## H7. 分量の過不足

- [ ] 全体の分量が目的・想定読了時間に対して長すぎないか <!-- 例:「長すぎる」「情報過多。重すぎる」-->
- [ ] appendix が本編理解に不要な情報で肥大化していないか <!-- 例:「appendix長すぎ」-->
- [ ] 必要な論点が薄すぎて説得力を欠いていないか <!-- 例:「薄すぎる」「内容もっとこくしたい」-->
- [ ] 圧縮のために必要な文脈・説明を削りすぎていないか <!-- 例:「過度に表現を圧縮しないで記載して」-->

## H8. ファイルの機械的整合

- [ ] XLSX の計算式が生きているか <!-- 例:「計算式死んじゃってる」「合計金額0になってるよん」-->
      （実行手順は `SKILL.md` を参照）
- [ ] XLSX を品質ゲート（`~/.claude/skills/xlsx/xlsx_quality_gate.py`）に通したか。freeze pane の選択不整合、折り返しセルの行高不足（文字切れ）、非表示行列が残っていないか <!-- 例: 2026-08-31 業務棚卸xlsxで受領版由来の12件を検収前に発見 -->
- [ ] XLSX を開いた直後の見え方が正常か（ズーム倍率が極端に小さくないか、ウィンドウ位置とサイズが常識的か。`sheet_view.zoomScale` と `wb.views[0]` で確認）<!-- 例:「開いた時にめっちゃちっちゃい」-->
- [ ] 結合セルにかかる row-height 指摘は誤検知の可能性があるため、PDF 化画像で実際の文字切れを確認してから判定したか。
      品質ゲートの needed 値は結合幅を無視して先頭列幅だけで見積もるため過大。この値をそのまま行高に設定しない
      （注記行が不自然に分厚くなり、機械生成感が出る）。行高は実際の折り返し行数（結合幅ベース）に合わせて設定し、
      文字切れの有無は PDF で確認する <!-- 初出: 2026-08-31 非公開クライアントA社FTE算出xlsx。needed値どおりに208.5ptへ積んで差し戻し -->
- [ ] PPTX は `python -c "from pptx import Presentation; Presentation('<file>')"` で開封検証したか
- [ ] HTML の改行・タグが意図通り効いているか <!-- 例:「brがきいてない」-->
- [ ] 最新版のファイルを参照・納品しているか（古いバージョン混入なし）<!-- 例:「古いやつになってる」-->
- [ ] 関連ファイル（md/xlsx/pptx 等）が同期して更新されているか <!-- 例:「mdも更新しておいて」-->
