# /verify

指定された生成物を4層で検収する。
旧 `/request`、`/ux`、`verify/<...>/` ワークスペースを前提にしない。

## 定数

- `PERSONA_OBSERVATION_MAX_AGE_DAYS = 180`
- 形式ルール: このスキルと同じディレクトリの `house-rules.md`

ログ書き戻しの実装（検収ログへの記録、受け手の人物知見の参照・更新）は社内リポ側にあり、この公開版には含めない。
自分の環境で使う場合は、検収結果を保存する仕組みと、受け手情報を管理する仕組みを別途用意すること。

チャット出力、ログ、一時入力を含む日本語では U+2500、U+2014、U+2013 を使わない。
区切りには句点、読点、コロン、括弧を使う。

## 実行順序

次の順番を変えない。

1. 対象を確定する。
2. AskUserQuestion を2回使い、検収意図を取得する。
3. `artifact_scope` を確定する。
4. 受け手を特定し、検収に使う情報を選ぶ。
5. V1 から V4 を実行し、統合判定する。
6. 検収結果を記録する（記録方法は環境側で用意する）。
7. 再検収なら前回指摘の解消状況を比較する。
8. 結果をチャットへ提示する。

## 1. 対象の確定

引数で指定されたファイルまたはディレクトリを対象にする。
指定がなく、会話から一意に決められない場合だけ AskUserQuestion で対象を確認する。
選択を求める質問を通常の文章で返して待たない。

対象が存在しなければ検収を始めない。
絶対パスを確定し、再検収の照合に使えるよう記録しておく（ハッシュ計算や run_id の発行は社内実装に依存するため、本公開版には含めない）。

## 2. 冒頭の合意形成

検収開始時に必ず AskUserQuestion を2回呼ぶ。
既存資料から推定できても省略しない。
選択肢は対象と会話に合わせ、自由入力もできる形にする。
各 question は12文字以内の header、質問文、2個から4個の options、`multiSelect` を持つ有効なオブジェクトにする。
各 option は label と description を持つ。
自由入力用の Other はツールが追加するため、options へ重複して作らない。

最初の呼び出しで次の4問をまとめて聞く。

1. 本質的検収者は誰か。
2. どの状態に到達すれば十分か。
3. 今回のスコープ外は何か。
4. 一つでもあれば不合格となる致命条件は何か。

1問目から3問目は `multiSelect: false`、4問目は `multiSelect: true` とする。

2回目の呼び出しで次の2問をまとめて聞く。

5. 読後に取ってほしい行動は何か。
6. 本質的検収者のほかに見る人は誰か。

5問目は `multiSelect: false` とする。
6問目は `multiSelect: true` とし、「追加受け手なし」と、文脈から推定した候補または既定 persona を含む2個以上の options を用意する。
2回目の呼び出しには5問目と6問目の両方を必ず含める。
ツールが引数不正を返した場合はオブジェクトを直し、2問を含む同じ呼び出しを成功するまで再試行する。
片方だけを聞いて後続へ進まない。

生成前に別の確定記録があり、その内容を今回の回答としてレビュー担当者が指定した場合は `intent.captured_at: pre_generation` とする。
それ以外は `intent.captured_at: at_verification` とし、表示では必ず「検収時（事後定義）」と書く。

本質的検収者が不明でも中止しない。
既定 persona（抽象的な意思決定者像）を使い、V4 と総合判定を `needs_confirmation` にする。
本質的検収者以外の回答が不明な場合も中止しない。
不明な回答を使う V2 だけを `needs_confirmation` にする。

## 3. artifact_scope

対象の用途、保存場所、会話から次の4値のどれかを推定する。

- `external`: 特定の顧客や社外関係者へ渡すもの。
- `internal`: 社内の検討、運用、意思決定に使うもの。
- `public`: Web、記事、登壇など不特定多数へ公開するもの。
- `hiring`: 候補者、採用広報、選考に使うもの。

推定根拠が競合する場合だけ AskUserQuestion で確認する。
この確認も選択肢を通常の文章で聞かず、必ずツールを使う。

## 4. 受け手の特定

本質的検収者と追加受け手を1人ずつ特定する。
実在人物であれば、確認済みの呼称・所属など、判明している範囲の情報だけを使う。
推定した別名や未確認情報を事実として扱わない。
抽象的な受け手で該当者がいなければ、既定 persona（抽象的な意思決定者像）として扱う。

受け手ごとの判断特性・傾向をどこかに保持している場合は、今回の判定に実際に使う観測だけを選び、各観測の日付・本文・出典・裏付けの強さを保持する。
裏付けの弱い観測は不合格の根拠にせず、追加確認が必要な理由としてだけ使う。
観測日から実行日までが180日を超える情報を V4 に使った場合、V4 と総合判定を `needs_confirmation` にする。
古い情報を使わなかっただけでは判定を落とさない。
相反する観測は両方を提示して総合判定を `needs_confirmation` にする。

## 5. 4層検収

V1、V2、V3 をそれぞれ1体のサブエージェントへ割り当てる。
V4 は本質的検収者と追加受け手の1人ごとに1体を割り当てる。
独立して実行できる部分は同時に開始する。
各担当は判定、指摘、成果物内の位置、根拠の位置を返す。
本体は結果を統合し、重複を除く。

### V1 形式

`house-rules.md` の H1 から H8 を1項目ずつ判定する。
H2 の前に `~/.claude/rules/document-tone-rules.md` を読む。
説明文書の段落と論証は `~/.claude/skills/japanese-tech-writing/SKILL.md` に従う。

言い回しの不自然さは R1 から R7 の照合では拾えないため、機械検査を併せて回す。
成果物からテキストを抽出し、`~/.claude/skills/japanese-tech-writing/scripts/njlint.sh --mode slide <file>` を実行する。
記事やレポートなど地の文が主体の成果物は `--mode prose` を使う。
findings は Fail ではなく**要確認**として検収レポートに載せ、直すか残すかの判断を添える。

H1 はテキストだけで判定しない。
HTML はブラウザでスクリーンショットを撮る。
PPTX と XLSX は画像化するか PDF 化して画像を確認する。
PDF はページを画像化して確認する。

PPTX では次の検査も実行する。

```bash
python3 ~/.claude/skills/verify/pptx_jp_wrap_check.py "<file.pptx>"
```

XLSX は `python3 ~/.claude/skills/xlsx/xlsx_quality_gate.py "<file.xlsx>"` を実行し、開封、数式エラー、表示崩れを確認する。
freeze pane の選択不整合、折り返しセルの行高不足、非表示行列の指摘は原則修正対象。
ただし結合セルにかかる row-height 指摘は、ゲートが単一列幅で必要高さを計算する誤検知の場合があるため、PDF 化した画像で実際に切れているかを確認してから判定する。
開いた直後の見え方（ズーム倍率、ウィンドウ位置とサイズが常識的か）も `sheet_view.zoomScale` と `wb.views[0]` の値で確認する。
PPTX は `python-pptx` でも開封できることを確認する。

H6 の表記ゆれ判定では次の手順で機械スキャンする。対象は html/md/pptx。
pptx は `unzip -p file.pptx 'ppt/slides/*.xml'` でテキストを抽出してから照合する。
表記ゆれペアの両方が同一成果物に出現したら WARN として一覧化する。

```bash
grep -lE 'サーバー' <target> | xargs -I{} sh -c 'grep -qE "サーバ[^ー]|サーバ$" "{}" && echo WARN: {}'
```

H2 見出しのタイトル抽出は次の手順で行う。抽出は機械、通し読みでの繋がり判定は人が読解で行う。
HTML は `h1`・`h2`・`.s-title`・`.title` クラスのテキストを抽出する。
PPTX は各スライドのタイトルプレースホルダを `python-pptx` で抽出する。

```bash
python3 -c "
from pptx import Presentation
prs = Presentation('<file.pptx>')
for i, slide in enumerate(prs.slides, 1):
    if slide.shapes.title:
        print(i, slide.shapes.title.text)
"
```

スライドとして成立させられない薄い内容は、無理に組まず文書形式（md/docx）への切り替えを提案する。

`artifact_scope` に応じて重点を変える。

- `external`: 宛先、敬称、顧客向け表現、機密露出、共有時の見え方。
- `internal`: 意思決定事項、担当、期限、内部用語の一貫性、配布範囲。
- `public`: 公開可能性、アクセシビリティ、権利表記、公開画面の見え方。
- `hiring`: 候補者体験、公平な表現、選考情報の扱い、個人情報の露出。

### V2 意図適合

冒頭回答の本質的検収者、達成したい水準、スコープ外、期待する行動に照らす。

- 達成したい水準を項目へ分け、各項目を個別に判定する。
- スコープ外の内容が入り込んでいないか確認する。
- 本質的検収者に必要な情報が前面にあるか確認する。
- 読後に期待する行動へ到達できる構成か確認する。
- 目的から外れた網羅や論点拡散を確認する。

致命条件に該当した場合は V2 と総合判定を `fail` にする。
回答が不明な項目は推測で補わず、対応する V2 判定を `needs_confirmation` にする。

### V3 事実整合

成果物から次の要素を自分で抽出する。

- 数値、日付、割合、件数。
- 人名、会社名、製品名、制度名などの固有名詞。
- 金額、単価、契約条件。
- 判断を左右する事実主張。

対象の近くにある sources、会議記録、参照資料、リポジトリ内の一次資料を先に探す。
根拠が見つかった主張をレビュー担当者へ再確認しない。
根拠が見つからない主張だけをまとめ、AskUserQuestion で出典または扱いを確認する。
この追問を冒頭6問へ追加しない。
選択を求める場合は通常の文章で返して待たず、必ずツールを使う。

重要な主張の根拠欠損、根拠との矛盾、未承認の金額掲載は `fail` とする。
資料だけでは根拠の有無を確定できない場合は `needs_confirmation` とする。

`artifact_scope` に応じて次も確認する。

- `external`: 顧客情報、契約条件、未公開情報、社外へ出せない内部参照。
- `internal`: 意思決定の根拠、最新性、内部数値の版、参照先の到達性。
- `public`: 公開根拠、引用と権利、公開済み情報との整合、個人情報。
- `hiring`: 候補者情報、求人条件、雇用表現、評価根拠、採用上の機微情報。

### V4 受け手印象

受け手1人につき1体が、その受け手の立場で対象全体を確認する。

- 達成したい水準に到達できるか。
- 懸念や誤解を招く箇所がないか。
- 期待する行動を取りやすいか。
- 受け手に不要な箇所、説明不足な箇所がないか。

判断特性を根拠に使う場合、出力へ次の2点を必ず並べる。

1. 使った観測の本文と出典。
2. その観測から判定した成果物の位置。

一般化した人物像だけで判定しない。
既定 persona を使った箇所は、実在人物の観測と区別して書く。

## 6. 統合判定

各層は `pass`、`fail`、`needs_confirmation`、`not_run` のいずれかにする。
総合判定は `fail`、`needs_confirmation`、`pass` の順で優先する。
`not_run` は優先比較から除外する。
4層すべてが `not_run` の場合は `needs_confirmation` にする。

指摘には一意な `id` を付ける。
同じ対象の再検収で同じ指摘が残っている場合は、前回と同じ id と summary を使う。
重大度は `fatal`、`major`、`minor`、`confirmation` のいずれかにする。
状態は `open`、`resolved`、`waived` のいずれかにする。
`waived` はレビュー担当者が非対応を選んだ場合だけ使い、理由を残す。

## 7. 検収結果の記録

対象の絶対パス、scope、意図取得時点、6回答、参照した観測、4層結果、指摘を、再検収で参照できる形で記録する。
記録先の形式・保存場所（単一ログファイルにするか、別のDBにするか等）は利用環境に合わせて決めてよい。ログ書き戻しの実装は社内リポ側にあり、この公開版には含めない。

## 8. 再検収

同じ対象の過去の検収結果があれば、開始前に直近の記録を読む。
前回指摘を検査項目へ加えるが、4層の全検収は省略しない。
同じ問題は前回と同じ finding id を使う。
前回指摘を `resolved` と `unresolved` に分け、新規指摘を別に示す。

## 9. 提示形式

次の順でチャットへ提示する。

```markdown
# Verify 結果

対象: <絶対パス>
意図取得: <生成前 | 検収時（事後定義）>
scope: <artifact_scope>
総合判定: <pass | fail | needs_confirmation>

## 層別結果

### V1 形式
### V2 意図適合
### V3 事実整合
### V4 受け手印象

## 参照した人物観測

## 指摘

## 前回指摘の解消状況
```

V4 では観測行と成果物位置を必ず表示する。
前回の記録がなければ「前回指摘の解消状況」は省略する。
最後に検収結果の記録先を示す。
