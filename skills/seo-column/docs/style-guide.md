# SEOコラム 執筆スタイルガイド

対象: `content/column/*.md` を新規執筆するsubagent。品質基準は公開済み1本目 `content/column/what-is-ai-transformation.md`(以下「1本目」)。迷ったら1本目の該当箇所を読んで揃えること。
スキーマ定義: `src/content.config.ts` の `column`。レンダリング: `src/pages/column/[slug].astro`。

## 1. Frontmatter仕様

```yaml
---
title: メインKW前方一致・全角30〜32字前後
slug: 英数ハイフンのURLスラッグ(kebab-case、Phase0のoutline.mdで確定済みのものを使う)
category: カテゴリ名(outline.md/link-matrix.mdの表記に合わせる。例: AX/DX)
description: 80〜120字。検索結果スニペット用。メインKW+サブKW1つを含め「何が書いてあるか」を要約
excerpt: 60〜100字。一覧カード用(2行clampで表示される)。descriptionより口語寄りでよい
publishedDate: 'YYYY-MM-DD'  # 公開予定日。outline.mdの公開日程に一致させる
updatedDate: 'YYYY-MM-DD'    # 初稿時はpublishedDateと同値。リライト時のみ更新
author: 株式会社ピネアル      # 固定値
keywords:                    # メインKW+表記ゆれ+サブKW。5〜7個
  - メインKW
  - サブKW(ロングテール)
  - ...
faq:                          # 3〜4問。サブKW/検索意図の取りこぼしを拾う
  - q: 疑問形の質問文(サブKWを含む)
    a: 2〜4文の完結した回答。本文の要約でよいが本文と一言一句同じにしない
# status は付けない(量産記事は publishedDate の未来日付フィルタで公開制御。下記参照)
---
```

**title**: 32字前後だが厳密な上限ではない。1本目は40字で許容範囲内(判断基準は「メインKWが先頭にあるか」「体言止めで冗長でないか」)。`<title>`タグは `{title}｜株式会社ピネアル` と自動連結される(+9字)ので、40字を超える場合は本当に削れないか一度見直す。
**description/excerpt**: 両方埋める。descriptionはSERP用で硬め、excerptは一覧カード用でやや柔らかめ、と役割を分ける(1本目参照: description92字/excerpt72字)。
**status**: 量産記事には**付けない**。公開制御は `publishedDate` の未来日付フィルタ(`src/lib/content.ts`、JST基準、2026-08-04実装済み)が担う: レビューはmainマージ前のPRで行い、マージ後も公開予定日までビルドから自動除外される。`status: draft`(`HIDDEN_COLUMN_STATUSES`)は「公開日を過ぎた記事を緊急非公開にする」際の手段として残す。

## 2. トーン&マナー

- 文体は **です・ます調**。体言止めの多用は避ける(見出し・箇条書きの項目名は除く)
- 常に **経営視点(なぜやるか・成果につながるか)と現場視点(実際どう進めるか・何が詰まるか)の両方**を書く。どちらかに偏らない
- 断定しすぎない。「〜すべき」より「〜が定石です」「〜が現実的です」「〜の近道です」。ただし曖昧にぼかしすぎず、言い切れることは言い切る(「〜が最も多い失敗です」等の事実整理は断定してよい)
- **数値は捏造しない**。実数を使うのは既公開のcases/topics記事にある数値のみ。裏付けのない実数を「多くの企業で」等の無出典の頻度表現に言い換えて残すのも不可(補足7-2)。数値・頻度への言及自体を削るか、読者が辿れる出典を付ける
- 一人称は使わない。ピネアルへの言及は「ピネアルは」(三人称・社名)。読者への呼びかけは「自社の場合」「御社の」程度に留め、過度に馴れ馴れしくしない
- 誇張語(「劇的に」「圧倒的に」「必ず」「絶対に」)は使わない。「大きく」「着実に」「一気に」程度まで

## 3. 記事構成3パターン

Phase0のoutline.mdで各記事に指定される検索意図に応じて選ぶ。同じ型の量産感を避けるため、同カテゴリ内で①②③を混ぜる。

### ①解説型(1本目がこの型。「〜とは」系のピラー記事向け)

1本目のh2/h3分解:

```
(リード文、H2の前・KWを最初の100字以内に配置)
## [KW]とは                          … 定義
## なぜ今、[KW]が注目されるのか        … 背景
   ### 背景1 / 背景2 / 背景3
## [KW]と[比較対象]の違い             … 比較(表)
## [KW]の3つの領域                    … 構造整理(番号付きリスト)
## [KW]推進の進め方【5ステップ】       … 手順
   ### ステップ1〜5
## [KW]推進でよくある失敗と対策       … 失敗パターン(箇条書き)
## [KW]を成果につなげるために          … まとめ+CTA
(以降、frontmatterのfaqが自動レンダリングされFAQセクションになる。本文中に別途FAQを書かない)
```

h2は7個前後、h3(ステップや背景の子見出し)は本文の入れ子として使う。「定義→背景→比較/構造→進め方→失敗パターン→まとめCTA」の順は崩さない。

### ②手順・How-to型(「〜のやり方」「〜する方法」系)

```
(リード文)
## [KW]とは(簡潔な前提共有、1〜2段落。①ほど厚くしない)
## [KW]を始める前に押さえること(前提条件・必要なもの)
## [KW]の手順【n ステップ】
   ### ステップ1〜n(各ステップに「やること」+「注意点」を1つずつ)
## [KW]でよくある失敗・つまずきポイント
## まとめ(+CTA)
```

手順は3〜7ステップ。各ステップの見出しは動詞で終える(「〜する」「〜を選ぶ」)。

### ③事例・比較型(「〜事例」「〜比較」「〜おすすめ」系)

```
(リード文)
## [KW]の基本(選定/活用の前提となる定義・軸を簡潔に)
## [比較軸/選定基準](表)
## 事例・パターンの紹介(2〜4件。既公開cases/topics記事に基づくもののみ実名可)
   ### 事例1〜n、またはパターンA〜C
## 自社に合った選び方(比較軸への立ち返り)
## まとめ(+CTA)
```

事例は一次情報バンク(`docs/seo-column/primary-sources.md`)の割当に従う。割当がない場合は実名を出さず「〜のようなケース」と一般化する。

## 4. 本文ルール

- **文字数**: 本文4,000〜8,000字(frontmatter除く、記号込みでのおおよその目安。1本目は約3,700字とやや短めだったため、量産分はこのレンジを守る)
- **リード文**: 見出し(H1)の直後、最初のH2が始まるまでの1〜2段落。**メインKWを最初の100字以内に登場させる**。「〜という言葉が当たり前になった一方で、〜」のように課題提起→本記事で解決することの順で書く
- **h2見出し**: サブKW(keywords配列の語)を無理なく含める。KWを詰め込んだ不自然な見出しにしない(例: 「AXの3つの領域」であって「AX 領域 3つ 一覧」ではない)
- **比較表**: 判断軸が2つ以上ある比較には表(Markdownテーブル)を1本以上入れる。列は「観点/軸」を1列目、比較対象を2列目以降。セル内は体言止め+短文
- **箇条書き**: 3項目以上を列挙する箇所、失敗パターン・チェックリスト的な箇所で使う。各項目の先頭語や重要語を太字にしてスキャンしやすくする
- **太字**: 1本目は本文3,500字に対し太字フレーズ約30箇所(h2セクションあたり3〜5箇所)。「フレーズ全体」ではなく**キーワード・言い切りの核**だけを太くする(文全体を太字にしない)。同じ語を何度も太字にしない

## 5. 内部リンクの書式(本文中3〜5本)

Markdownリンク構文で本文中に自然に埋め込む。アンカーテキストは**リンク先記事のメインKWを含む名詞句**にする(「こちら」「詳しくはこちら」は禁止)。

```markdown
具体的な進め方や実装の考え方は[AIトランスフォーメーション事業のページ](/ai)で、
実際の取り組みは[支援事例](/cases)でご覧いただけます。
```

配分ルール(全体計画`docs/seo-column-量産計画-2026-08.md`の内部リンク設計に準拠):

1. 自カテゴリのピラー記事へ必ず1本(例: `[AIチャットボットとは](/column/ai-chatbot-guide)`のように記事名をアンカーに)
2. 同カテゴリの関連記事へ1〜2本(サブKWの文脈で自然に。「〜については[プロンプトエンジニアリングの基本](/column/prompt-engineering-basics)で解説しています」のような形)
3. 事業ページ(`/ai` または `/marketing-creative`)or 事例(`/cases`、`/topics`)へ1本、まとめの直前かCTA直前に配置
- リンク先が自分より後に公開予定の記事の場合は、Phase0のlink-matrix.mdの指示に従い `<!-- [記事名](/column/slug) -->` の形でコメントアウトして仕込み、週次リンクパッチで有効化する(壊れたリンクは絶対に公開しない)
- 「関連記事」欄は自動選定(`getRelatedColumns`)なので本文と別に手動で作らない

## 6. CTAパターン(記事末尾)

最後のh2セクション(まとめ)の中で、太字で要点を締めた直後に導線を置く。1本目の実例:

```markdown
ピネアルは、**PoCで終わらせず本番運用まで実装する**ことを掲げ、業務プロセス改革・
AIソリューション構築・AI人材育成を一気通貫で支援しています。具体的な進め方や実装の
考え方は[AIトランスフォーメーション事業のページ](/ai)で、実際の取り組みは
[支援事例](/cases)でご覧いただけます。

「自社の場合、何から始めればいいか」を整理したい段階でも構いません。
[無料相談](/contact)から、現場の課題をそのままお聞かせください。
```

型: ①ピネアルの立場・強みを一言で言い切る→②事業ページ or 事例へのリンク→③一段落おいて`/contact`への誘導(「〜な段階でも構いません」「まずは〜からお聞かせください」等、ハードルを下げる言い回し)。事業ページはカテゴリに応じて `/ai`(AX系)か `/marketing-creative`(CX/マーケ系)を選ぶ。

## 7. NG集

- **数値の捏造**: アクセス数・改善率・導入社数などの実数は、既公開cases/topics記事に明記されている値以外使わない。「多くの現場で」「一定数の企業が」など無出典の頻度表現への言い換えでの温存も不可(補足7-2)。削るか出典を付ける
- **クライアント名の新規出し禁止**: 実名を出せるのは既公開のcases/topics記事に載っている企業(例: 製造業A社、化学メーカーB社)の範囲のみ。それ以外は「ある製造業の企業では」等、匿名・一般化した表現にする。新規の実名掲載は先方承認が必須(過去の実名掲載記事の承認フロー実績を参照。個別にレビュー担当者へ確認が必要な案件なので勝手に実名化しない)
- **クライアント名に敬称を付けない**: コラムでは「塩尻市様」ではなく「長野県塩尻市」と書く。コラムは第三者的な解説記事であり、`content/topics/` の支援事例記事(クライアント向けに「〇〇株式会社様」と敬称を付ける)とは扱いが違う。「お客様視点」のような一般名詞や、マスキング例の架空人物(「A社の田中様」)は対象外
- **誇大表現**: 「業界No.1」「絶対に成功する」「劇的に改善」等の実証不能な最上級・断定表現は使わない
- **他社比較での断定的優劣**: 特定の他社サービス・製品名を挙げて「A社よりB社が優れている」と断定しない。比較軸を示して読者が判断できる形にとどめる(「〜という軸で選ぶ企業が多い」)
- **壊れた内部リンク**: 未公開記事への直リンクは禁止。上記5節のコメントアウト運用に従う
- **本文中への手動FAQ重複**: FAQはfrontmatterの`faq`配列のみに書く。本文中に別途「よくある質問」見出しを作らない(テンプレート側で自動レンダリングされ二重になる)

## 補足2: 「ピネアルの現場から」ブロック(2026-08-04追加・全記事必須)

一次情報が本文に埋もれて見えない問題への対策。**全記事に1箇所**、本文中盤〜後半(まとめh2の前まで)に以下の形式のblockquoteを置く:

```markdown
> **ピネアルの現場から**
> (3〜6文。primary-sources.mdにある事実のみで構成し、固有名詞または実数値を最低1つ含める。
> 例: 支援事例の実名+数値/自社DOGFOODING運用の具体/著書・登壇/本サイト自身の実装)
```

- 既存の本文中に散在するピネアル言及はこのブロックへ統合してよい(重複した自社紹介を2箇所に書かない)
- まとめセクションのCTA(§6)とは別物。CTAは従来どおり残す
- 数値・事例の創作禁止、実名は既公開記事の範囲のみ(§7)は本ブロックにも適用
- **記事テーマと事例ツールの一致チェック(2026-08-13追加)**: 特定ツール名を冠した記事(ChatGPT/Copilot/Dify/Gemini/Claude等)に別ツールの事例を入れない。当該ツールの事例が`primary-sources.md`に無い場合のみ別ツール事例を使ってよいが、その際は**事例側のツール名を本文に明記し、記事テーマのツールの成果と誤読されない書き方にする**(例: 「ツールがMicrosoft Copilotのケースでは〜」)。ツール名の判別は`primary-sources.md`の各事例の記載を正とする
- **実名事例への内部リンク必須(2026-08-13追加)**: 実名で挙げた支援事例には、該当する公開済み`/topics/`または`/cases/`記事への内部リンクを付ける(アンカーは事例内容を表す名詞句、URLは末尾スラッシュ)。このリンクは§5の本文リンク3〜5本の配分とは別枠で数える。該当記事が無い実名は§7のとおりそもそも使えない

## 補足3: 図版ルール(2026-08-04・パイプラインv3で改訂)

**正本は `docs/seo-column/figure-design.md`**(図種カタログ・要否判断・BPMN規約・デザイン規約・作図時の落とし穴)。ここには要点だけ書く。

- **図の要否は記事ブリーフ(Stage 1)で決める**。「全記事に最低1点」というv2のノルマは廃止。3要素以上の関係・順序と分岐・2軸比較・実測データ・実操作のいずれかがある場合に入れる。目安はピラー2〜4点、個別記事0〜2点。**0点も正解**
- **形式**: 概念図・比較・ステップ図はSVG直書き。BPMN業務フローとシステム構成図はdrawio(`drawio --export --format svg`)。drawioソースは `docs/seo-column/figures/{slug}/` に置き、書き出したSVGだけ `content/images/column/{slug}/` へ
- **参照**: `![何が描かれているかの説明](/images/column/{slug}/fig-1.svg)` の直後に `*図N: 図から読み取ってほしい結論*` のキャプション1行。SVG内の文字は検索エンジンに読まれないので、要点は必ずキャプションで本文テキストとして残す
- **サイズ・配色**: viewBox幅1200固定、最小文字16(viewBox上)。白背景で固定(ダークモード切替は実装しない)。ブランド赤 `#d21e2d` は1図あたり1〜2箇所まで
- **禁止**: 図中の数値・事例の創作、本文と図で同じ内容の繰り返し
- 本文図版とサムネイルは別に管理する。サムネイルは2026-09-04選定済みの `figures/marketing-thumbnail/template.html` を使用し、`thumbnail` に画像パスを設定する（2026-09-07更新）。本文図版がない記事も、本文の表などを引用して作成する。本文図版0点をサムネイル省略の理由にしない。サムネイルは一覧・記事冒頭・OG画像に使われる。

## 補足6: 具体性ルール(2026-08-13追加・全記事適用)

抽象的なトレンド記述・一般論は不可。「〜する企業が増えています」「効率化が期待できます」のように、主語が「企業」「現場」「多くの組織」で固有名詞も機能名も無い段落は、書いた時点でリライト対象。

- **動向・トレンドに触れる文は、実在の機能名・ツール名を挙げる**(例: Deep Research、カスタムGPT、Claude Code、GitHub Copilot)。機能名は執筆時点の現行名称をWebSearchで確認してから書く(§7の捏造禁止と両立する。実在して検証可能な固有名詞を避けることは「安全側」ではなく品質劣化)
- **挙げた機能は、その記事内の業務例・テンプレ・事例に接続する**。「この記事のこの業務なら、この機能でこう変わる」の形まで書き切る。機能名の羅列だけでは足りない
- **ピネアル自身の運用を実例として使ってよい**。5チームエージェント体制(23時バッチ・朝7時ブリーフィング・Slack起動)、UPRESSによる自社コラム制作と外部提供(/topics/service-ai-media-by-upress/)等、サイト内に出典があるものに限る。「ピネアルの現場から」ブロックとの重複は避け、記事の主張の証拠として置く
- 効果・変化を述べるときは「誰の・どの業務が・どう変わる」まで具体化する。程度の数値は出典があるときだけ書く
- ブリーフ(Stage 1)の段階で「この記事で使う具体(機能名・自社運用・事例)」を列挙しておき、Stage 3の初稿がそこから外れて一般論に流れていないかをStage 6の前に確認する

## 補足7: 2026-08-14レビューサイクルからの追加ルール(全記事適用)

PR #175〜#179のcodexレビュアーによる敵対的レビューで実際に検出された問題を恒久ルール化する。

### 7-1. 匿名事例のモザイク再特定チェック

実名を伏せてリンクを張らないだけでは匿名化にならない。業種・部門、対象業務、製品実名、時期、成果数値・規模・地域、固有の工程・ストーリーは、単独では無害でも組み合わせで効く**準識別子**である。**その全部または一部の組み合わせが、公開済みの `content/topics/` と `src/data/cases.ts`(公開 /cases の正本)を含むサイト全体、および合理的に参照できる外部公開情報と突き合わせて一意に特定できないか**を、執筆時とレビュー時の両方で確認する。

- 既定の対処は**識別子の間引き**: 製品・サービスの実名(例: Power Automate、AI Builder)、稼働時期(年月)、契約期間・本数などの具体数は落とす。業務内容・成果数値・段階発展のストーリーは残しやすい要素だが、これらも準識別子になりうるため無条件で安全ではない(組み合わせで再評価する)
- 匿名事例から、同一クライアントの実名topics/cases記事へ内部リンクを張らない(リンク自体が匿名を破る)
- どの識別子を残すか(=残存する再特定リスクの受容)はレビュー担当者の判断事項。執筆側で勝手に決めず、受容の判断はPR・レビュー記録に残す
- 同じ事例に触れるFAQ・導入文・まとめ・図版も本文と同じ粒度に揃える(本文だけ直してFAQに旧識別子が残る事故が実際に起きた)

### 7-2. トレンド断定は出典があるときのみ

「2026年現在は〜へ重心が移りつつある」のような**市場全体の動向断定は、出典が無ければ書かない**。製品にその能力があること(検証可能)と、市場がそちらへ動いていること(要出典)は別の主張。出典が無い場合は「ピネアルの支援現場では〜が増えている」と自社の観測範囲に限定する。自社観測として書く場合も、実在の案件・社内記録で根拠が辿れる内容に限る(観測の体裁を借りた一般論の温存はしない)。

### 7-3. ツール仕様は正確に書く

挙げたツールの動作仕様(例: Claude Codeのスキルは常時読込ではなく必要時読込)は、公式ドキュメントで確認できる粒度で書く。名称だけでなく挙動の記述も捏造禁止の対象。プラン・設定によって挙動が変わるもの(学習利用・データ保持・監査ログ等)は、どのプラン・どの設定の話かを特定して書き、記事の公開直前に名称・仕様が現行のままかを公式情報で再確認する(改称・機能統合が頻繁にあるため)。再確認の結果は、参照した公式ページのURL・確認日・対象プランをPR本文またはコミットメッセージに記録し、後から検証を辿れるようにする。

### 7-4. 構築主体と実行主体を混同しない

コーディングエージェントの話は、対象の構成に応じて「エージェントが仕組みを**作る**」と「出来上がったワークフローが**自動実行する**」を区別して書く。構築後は固定ワークフローが回る構成なら、エージェントが毎回実行するように読める書き方をしない。逆に実行時にエージェントが判断する構成(agenticなワークフロー)を扱うなら、その旨を明示する。本文と図版で層のずれが出やすいので、図版のラベルも同じ区別で揃える。

### 7-5. ツール軸の既定はコーディングエージェント

新規執筆・リライトで、**ツール中立な一般論として現行トレンドを書く場合**の既定軸は、Dify・n8nのようなワークフローツールではなく**Claude Code・GitHub Copilotのようなコーディングエージェント**とする。ただし記事テーマへの適合が優先で、Dify/n8nがテーマの記事や非開発職向けテーマにまで機械的に適用しない。既公開事例の事実記述(ダイキン工業のDify講座等)は書き換えない。対比する場合は「ノーコードでのエージェント構築」対「コードベースでの内製化」のように実態の差で書く。

### 7-6. 公開前の敵対的レビュー

対象は、(a)全新規記事、(b)匿名性・数値・製品仕様・トレンド記述のいずれかに触れる全改修(1文の追加でも該当すれば対象)。マージ前に別のレビューエージェントへ敵対的レビューを依頼する(社内では専用のレビューチームを使っているが、実装は本公開版に含めない)。観点は本補足7の各項+§7 NG集。終了条件は「High以上の指摘がゼロ」または「残存指摘をオーナー(レビュー担当者)が受容した記録が残っている」こと。1往復で終わらなければ解消まで再チェックを繰り返す。
