# SEOコラム 執筆パイプライン v3(2026-08-04)

> 2026-09-06更新（#327）: 工程の責任分担は維持する。公開ペースと進捗の実態は案件固有の進行管理ドキュメント（本公開版には非収録）を参照。執筆完了・AI確認・レビュー担当者の内容確認・実公開を別々に記録し、未確認原稿はmainへマージしない。未来日付はレビューの代わりにならない。

v2からの変更点は一言でいうと、**図版と一次情報を「執筆の後工程」から「設計の産物」に移した**こと。

v2は「書いてから図を足す」構造だったため、図が本文の装飾に留まり、記事ごとに何の図が要るのかを誰も決めていなかった。v3では記事1本ごとに**ブリーフ**を作り、そこで一次情報の割当と図版計画を先に確定する。執筆はブリーフの実装作業になる。

正となる設計資料(キーワードマップ)と全体計画は案件固有の計画ドキュメント(本公開版には非収録)を参照。

## 工程一覧

| # | 工程 | 担当モデル | 入力 | 出力 |
|---|---|---|---|---|
| 0 | 一次情報プール整備 | haiku(並列部隊) | 社内外の各ソース | `facts/*.md`(事実カード) |
| 1 | **記事ブリーフ設計** | **fable**(上限時 opus) | outline(非収録) + 事実カード + link-matrix(非収録) | `briefs/{slug}.md` |
| 2 | 素材調達(スクショ・画像) | haiku(並列部隊) | ブリーフの素材オーダー | `content/images/column/{slug}/` + 素材台帳 |
| 3 | 初稿執筆 | sonnet | ブリーフ | `content/column/{slug}.md`(図版はプレースホルダ) |
| 4 | **図版生成** | **opus** | ブリーフの図版計画 + 素材 | SVG/drawio + 本文への埋め込み |
| 5 | humanizeリライト | sonnet | `humanize-column.md` | リライト版本文 |
| 6 | 機械チェック | Python | `scripts/check-column.py` | OK/NG |

工程1と4を上位モデルに置くのがv3の骨子。**設計(何を作るか)と作図(どう見せるか)が品質を決める**ので、そこにコストを寄せる。執筆・リライトはブリーフが正確なら sonnet で足りる。

## Stage 0: 一次情報プール整備(haiku並列部隊)

記事ごとに一次情報を探すのではなく、**先にプールを作って設計工程が引けるようにする**。

### ソース別の担当割り

| 担当 | ソース | 取りに行くもの |
|---|---|---|
| 1 | 既存 `content/cases/*.md` `content/topics/*.md` | 公開済みの実名事例・実績数値・導入経緯 |
| 2 | 社内ナレッジベース | 社内の運用知見・失敗パターン・意思決定の経緯 |
| 3 | Notion Projects DB(`ntn` CLI) | 進行中案件の非機密な範囲の事実(業種・課題類型・期間) |
| 4 | 自社サイト実装そのもの | 構造化データ・LLMO実装・本コラム運用自体の設計 |
| 5 | `primary-sources.md`(非収録) §④ | 社内ヒアリング回答(2026-08-04) |

### 事実カードの形式

`docs/seo-column/facts/{source}-{nn}.md` に1事実1ファイル。

```markdown
---
id: cases-07
fact: <事実を1文で。数値があれば数値ごと>
source: <ファイルパス or URL or 「社内ヒアリング2026-08-04」>
disclosure: public | anonymized | internal-only
categories: [11, 12]     # 使えるカテゴリ番号
figure_material: yes|no  # 図版の素材になりうるか
---

<補足。前後関係、使うときの注意、言い換えの許容範囲>
```

- `disclosure: public` — 既公開のcases/topics記事に載っている。実名で書いてよい
- `disclosure: anonymized` — 事実は正しいが社名は出せない。「製造業の大手企業で」等に言い換える
- `disclosure: internal-only` — 記事に使わない。プールには残すが設計工程が引かない

**判定の原則**: 迷ったら `anonymized` に倒す。新規のクライアント実名出しは先方承認が要る(過去の実名掲載記事の承認フロー準拠)。

### 禁止事項

- **数値の捏造禁止**。出典が辿れない数字はカードにしない
- 個別契約額・個人実名は `internal-only` 固定
- 実名不可の企業名・架空の企業名は `scripts/check-column.py` の `FORBIDDEN` 定数を参照(自社の運用に合わせて内容を差し替えて使う)

## Stage 1: 記事ブリーフ設計(fable / 上限時 opus)

v3で新設。記事1本につき `docs/seo-column/briefs/{slug}.md` を1枚作る。

### ブリーフに書くこと

```markdown
# {slug} ブリーフ

## 1. 読者と検索意図
- 想定読者と、その人が既に知っていること/知らないこと
- 検索意図(知りたい / 比較したい / やり方を知りたい)
- この記事を読んだ後に何ができるようになるか

## 2. 構成(h2確定)
アウトラインからの変更があれば理由も書く。

## 3. 一次情報の割当
| 使う場所 | 事実カードID | 表現 | disclosure |
|---|---|---|---|
| 「ピネアルの現場から」 | cases-07 | 実名可 | public |
| h2-3の導入 | brain-12 | 業種のみ | anonymized |

## 4. 図版計画
| No | 何を示す図か | 図種 | 形式 | 配置 | 必要素材 |
|---|---|---|---|---|---|
| 1 | LLMOとSEOの守備範囲の重なり | 概念マップ | SVG | h2-1直後 | なし |
| 2 | 導入判断の分岐 | 業務フロー(BPMN) | drawio | h2-4末尾 | なし |

各図に alt文とキャプション文を確定して書く。**図が不要と判断した記事は「図版なし」と理由を書く**。

**走査対象は本文全体**。解説パートだけでなく「ピネアルの現場から」ブロックも図版候補として見る。自社の運用実態を書くブロックは、組織構成・時間帯のサイクル・出し分けの条件など**構造を持つ記述が1段落に畳まれやすい**ため、図の適性がむしろ高い(バッチ1では10本中2本がこれに該当したが、初版のブリーフは全本で走査対象から外していた)。落とす場合も「§図にしなかったもの」に理由を残す。落とす典型は、他の図とすでに同じ主張を持つ場合と、同じ記述が複数記事に要約版で入っており1本に集約すべき場合。

## 5. 素材オーダー(Stage 2への指示)
| No | 撮るもの | URL/手順 | 撮影範囲 | 権利確認事項 |
|---|---|---|---|---|

## 6. 内部リンク
link-matrixの該当行を転記。公開日が自分より後の記事はコメントアウト指定を明記。
```

### 図版計画がv3の肝

図の要否と図種は、**本文を書く前に**決める。理由は3つ。

1. 図が決まっていれば、本文は「図で示すこと」を文章で繰り返さずに済む。認知負荷が下がるのは図を足したからではなく、**図と文章の役割分担ができたから**
2. 図に必要な素材(実測値・スクショ)が事前に分かるので、Stage 2 が並列で走れる
3. 「毎回1点入れる」ノルマから外れる。要らない記事には入れない

判断基準と図種カタログは `docs/seo-column/figure-design.md` を参照。

## Stage 2: 素材調達(haiku並列部隊)

ブリーフの素材オーダーに従ってスクリーンショット・画像を集める。

### 撮影範囲(2026-08-04 レビュー担当者決定: 自社・外部ツール・作図をいずれも使う)

| 種別 | 例 | 権利上の扱い |
|---|---|---|
| 自社アセット | pineal.co.jp の画面、自社ダッシュボード、自社で作った実演画面 | 制約なし。**一次情報としても最強**なので優先 |
| 外部ツールUI | ChatGPT、GA4、Google広告管理画面 等 | **掲載可否の確認が必須**(下記) |
| 作図 | SVG/drawio | Stage 4 で生成 |

### 外部ツールUIを撮る場合の必須チェック

素材台帳に以下を記録してからでないと本文に載せない。

1. **利用規約・ブランドガイドラインの確認** — そのサービスがスクリーンショットの第三者掲載を許可しているか。要クレジット表記の有無
2. **写り込みチェック** — 個人名・メールアドレス・クライアント名・APIキー・アカウントID・実データが写っていないか。写っていたらマスクするか撮り直す
3. **鮮度** — UIは変わる。撮影日を記録し、古くなったら差し替え対象にする

判断がつかない場合は**外部UIを使わず作図に切り替える**。記事を止めない。

### 素材台帳

`docs/seo-column/briefs/{slug}.assets.md`

```markdown
| ファイル | 種別 | 出典 | 撮影日 | 権利判定 | 写り込みチェック |
|---|---|---|---|---|---|
| fig-3.webp | 外部UI | ChatGPT設定画面 | 2026-08-05 | 規約上OK(クレジット不要) | 済(アカウント名マスク) |
```

### 画像の仕様

- 形式: **webp**(既存サイトの主流。240件超がwebp)
- 幅: 1200px上限。ファイルサイズ 300KB を目安、超えたら再圧縮
- 置き場: `content/images/column/{slug}/`(`scripts/sync-images.mjs` が `public/images/` へ再帰コピーするのでサブディレクトリで問題ない)

## Stage 3: 初稿執筆(sonnet)

ブリーフに完全準拠。v2からの主な変更点は2つ。

- **図版はプレースホルダで置く**: `<!-- FIG:1 -->` の1行だけ書き、実際の埋め込みは Stage 4 が行う
- **一次情報はブリーフで指定された事実カードのみ使う**。執筆時に新しい数値や事例を思いつきで足さない

その他(文字数4,000〜8,000字、FAQ 3〜4問、frontmatter、CTA)は `style-guide.md` のとおり。

## Stage 4: 図版生成(opus)

ブリーフの図版計画に従って作図し、プレースホルダを実際の埋め込みに置換する。詳細規約は `figure-design.md`。

### 形式の使い分け

| 形式 | 使う場面 | 生成方法 |
|---|---|---|
| **SVG直書き** | 概念図・比較マトリクス・ステップ図・Before/After・時系列 | opusが直接SVGを書く |
| **drawio** | BPMN業務フロー・システム構成図。レーンや多数の分岐があり手書きSVGだと座標管理が破綻するもの | `.drawio` を書き、CLIでSVGにエクスポート |

drawio CLIは `/opt/homebrew/bin/drawio` で動作確認済み(2026-08-04。日本語ラベル・レーン・ブランド赤アクセントのSVG書き出しまで検証)。

```bash
scripts/drawio-export.sh {slug} N
```

- **drawioソースは `docs/seo-column/figures/{slug}/fig-N.drawio`**(`content/images/` に置くと `.drawio` ファイルまで公開されてしまう)
- 書き出し先は `content/images/column/{slug}/fig-N.svg`
- `drawio --export` を直接叩かない。CLIのSVG出力は背景が透過になり、ダークモードで図が読めなくなる。スクリプトが白背景の注入まで行う

### 本文への埋め込み

```markdown
[![AI検索最適化とSEOの守備範囲の重なりを示す図](/images/column/what-is-llmo/fig-1.svg)](/images/column/what-is-llmo/fig-1.svg)

*図1: LLMOはSEOの上位互換ではなく、重なりを持つ別の最適化領域*
```

- 絶対パス(既存記事の慣行と同じ)
- **画像は自分自身へのリンクで包む**(2026-08-04 レビュー担当者判断)。viewBox幅1200の図はモバイル(実表示342px)では文字が5px相当まで縮む。リンクにしておけばタップでSVG単体が開き、ブラウザのズームで読める。サイト側のCSS改修は不要で、`<a>` の下線は中身が `<img>` のみなら描画されない(実機確認済み)
- **alt は必須**。何が描かれているかを説明する。キーワードの詰め込みはしない
- **キャプションを図の直下に斜体1行**。SVG内の文字は検索エンジンに読まれないので、図の要点はキャプションで本文テキストとして残す(LLMO上の実利がある)

## Stage 5〜8

v2から変更なし。

- Stage 5 humanize(sonnet): `humanize-column.md` の適応仕様。**図の埋め込み行とキャプションは書き換え対象外**
- Stage 6 機械チェック: `scripts/check-column.py`。v3で追加する検査項目は下記
- Stage 7 レビュー担当者レビュー: PR単位。観点は内容の正誤と、会社として言ってよいか
- Stage 8 自動公開: `publishedDate` フィルタ + `daily-publish.yml`。**公開日到来時にリンクパッチの要否を確認する**(下記)

### Stage 8 付随作業: リンクパッチ(2026-08-16 パイプラインに組み込み)

未来公開記事へのリンクは執筆時にコメントアウトしてある(公開直後の404防止)。リンク先の記事が公開日を迎えたら、次の手順で解放する。自動では動かないため、**記事公開に関わるセッションの冒頭で必ず要否を確認する**。

1. `link-matrix.md`(非収録・案件固有の内部リンク表)の「前方参照一覧」と今日の日付を突き合わせ、リンク先が公開済みになった行を特定する
2. 該当記事の本文でコメントアウトを外し、生リンクに戻す
3. `link-matrix.md` の前方参照一覧から該当行を消す
4. `python3 scripts/check-column.py` で検査して PR

前方参照一覧が空なら作業なし。頻度は週1回程度で足りる(遅れても既存記事は壊れず、内部リンクが少ないままになるだけ)。

### チェッカーの図版検査(v3・実装済み 2026-08-04)

`scripts/check-column.py` に実装済み。ERROR は終了コード1でCIを落とす。

| 検査 | 判定 |
|---|---|
| 図版ファイルの実在(本文の `/images/column/...` が `content/images/` にあるか) | ERROR |
| alt が空でないこと | ERROR |
| 画像パスとリンク先(`[![alt](x)](x)` の2つのパス)が一致すること | ERROR |
| 図の直下の非空行がキャプション `*図N: …*` であること | ERROR |
| ファイル名 `fig-N` とキャプションの図番号が一致すること | ERROR |
| プレースホルダ `<!-- FIG:n -->` の残存 | ERROR |
| 素材台帳 `briefs/{slug}.assets.md` の権利判定欄が空でないこと | ERROR |
| ブリーフの図版点数と本文の図の数が一致すること | ERROR |
| 図版が自分自身へのリンクで包まれていること | WARN |
| 図があるのにブリーフがない | WARN |

ブリーフ側の点数は `図版点数: **N点**`(バッチ1形式)と `判定結果: **N点**`(パイロット形式)の
どちらでも読む。図を入れない記事はブリーフに「図版なし」と書けば0点として突合する。

## 監修者表記(2026-08-05 追加)

記事上部に1行、末尾にフルプロフィール(顔写真・略歴・書影・プロフィールリンク)を出す。
定義は `src/data/supervisors.ts`、描画は `src/components/common/SupervisorProfile.astro`。
frontmatter に `supervisor: <id>` があるときだけ表示され、JSON-LD には
`Article.editor`(Person)と `mainEntityOfPage.reviewedBy`(WebPage の @id 参照)が追加される。

**このフラグは Stage 7 のレビュー担当者レビューを通した記事にだけ立てる。**
執筆時にテンプレとして一律で付けない。中身を見ていない記事に監修者名を書けば、それは
事実と食い違う表示になる。レビュー前の記事はフラグなしで公開してよい(ブロックが出ないだけ)。

技術記事シリーズの確認状況と本人回答の記録は案件固有の記事レビュー台帳(本公開版には非収録)で管理する。
`npm run check:tech-review` は、未確認の監修表示と、確認対象の本文や画像の変更を検知する。

チェッカーは `supervisor` の値が `supervisors.ts` に定義済みのIDかを検査する(未定義なら ERROR)。
typoで黙って非表示になる事故を防ぐためで、フラグの有無そのものは検査しない。

## モデル割り当ての方針

| 工程 | モデル | 理由 |
|---|---|---|
| 一次情報収集・素材調達 | haiku | 手数が多く、判断より網羅性が要る |
| 記事ブリーフ設計 | fable(上限時 opus) | 記事の当たり外れがここで決まる。図の要否判断・一次情報の使い所は判断の質がそのまま成果物に出る |
| 執筆・humanize | sonnet | ブリーフが正確なら実装作業 |
| 図版生成 | opus | 図は情報設計そのもの。座標・階層・省略の判断を誤ると本文より害になる |

## バッチ1(執筆済み10本)への適用

2026-08-04 レビュー担当者判断: **本文は維持し、図版とhumanizeだけ遡及適用**。

1. 10本それぞれに**図版計画のみのブリーフ**を作る(Stage 1の§4だけ。fable)
2. 素材が要るものは Stage 2
3. Stage 4 図版生成(opus)
4. Stage 5 humanize
5. Stage 6 チェック → PRを更新してレビュー担当者レビューへ

一次情報は既に「ピネアルの現場から」ブロックとして各記事に入っているため、Stage 0 の遡及は行わない。バッチ2以降からフル適用。

## v2から変わらないこと

- 公開ペース(初週5本 → 以降1日1本)と公開自動化の仕組み
- 内部リンク3層構造とリンク切れ防止(コメントアウト → 週次リンクパッチ)
- スタイルガイド(トーン・構成・文字数・FAQ・CTA)
- 守秘ルール
- レビュー担当者のレビュー観点と負荷

## DLサンプル(ダウンロード資料)工程は別系統
